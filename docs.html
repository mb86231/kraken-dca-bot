Strategy

How DCA works, and why

Dollar Cost Averaging removes the need to time the market. Instead of buying a large amount at once, you buy a fixed amount at regular intervals. Over time this averages out the purchase price — buying more when prices are low, less when they're high.

This bot takes that further: it spreads buys evenly within a cycle so your available balance is deployed gradually, not in one hit. It also watches for significant price dips and buys opportunistically when they occur.

Mode 1  ·  Active
Recurring

You deposit fiat on the same day each month. The bot spreads buys evenly from one deposit day to the next, restarting the cycle automatically. Use this for ongoing monthly DCA.

Mode 2
Lump Sum

You deposit a fixed chunk once and set an end date. The bot spreads buys evenly until that date. Use this when you want to DCA a specific amount over a defined bear-market window.

How it works

The buy loop

On startup the bot executes an immediate buy, then enters a continuous polling loop. Every poll interval (default 5 minutes) it checks the current price and decides whether to act.

01

Calculate schedule

Reads available fiat balance and current price. Divides remaining hours in the cycle by the number of affordable buys to get the interval between buys.

02

Wait for next buy time

Sleeps until the next scheduled buy, waking every poll interval to check price and detect dips.

03

Dip detection

If the current price drops below the last buy price by the configured threshold (e.g. 5%), an extra buy fires immediately, subject to the cooldown window.

04

Deposit detection

If the fiat balance increases between polls (a new deposit arrived), the schedule is recalculated automatically.

05

Execute and record

Places a market buy order on Kraken for the configured crypto amount, then appends the trade to transactions.json and prints a portfolio summary.

Buy guards

Before every buy — scheduled or dip — these checks run in order. Any failure skips the buy with a warning.

1 In lump sum mode: if today is past dca_end_date, buying stops permanently.
2 If current price exceeds max_price, the buy is skipped. Avoids buying at all-time highs.
3 If this buy would push the cycle's total spend past max_monthly_amount, the buy is skipped.
4 If fiat balance is insufficient for the order, the buy is skipped.
Configuration

config.json reference

All settings live in config.json. API credentials must not be placed here — pass them as environment variables KRAKEN_API_KEY and KRAKEN_API_SECRET via a .env file that is never committed.

Field Type Description
mode string "recurring" or "lump_sum". Selects the DCA strategy.
trading_pair string Kraken asset pair. e.g. "XBTCHF" for BTC/CHF. Must match Kraken's exact internal naming.
deposit_day int 1–28 Day of month the cycle resets. The scheduled buy fires at buy_hour on this day. Defines the monthly spend period boundary. Unused in lump_sum mode.
buy_hour int 0–23 Hour of day the scheduled buy executes.
crypto_amount float > 0 BTC to buy per order. Kraken's minimum is 0.0001 BTC. Every scheduled and dip buy uses this amount.
dip_threshold_percent float 0–100 % drop below the last buy price that triggers an extra dip buy. e.g. 5.0 means a 5% drop.
dip_buy_cooldown_hours float ≥ 0 Minimum hours between two consecutive dip buys. Prevents over-buying during a prolonged crash.
poll_interval_seconds int ≥ 60 How often the bot checks price and conditions. Lower values catch dips faster but increase API calls.
max_price float or null Skip any buy if current price is above this value. Avoids buying at elevated levels. Optional — null to disable.
max_monthly_amount float or null Maximum fiat to spend per cycle (deposit day to deposit day). A buy that would exceed the limit is skipped. Optional — null to disable.
dca_end_date date or null ISO date string e.g. "2027-06-01". Required in lump_sum mode — buying stops after this date. Must be in the future.
config.json — recurring mode 
{
  "mode":                    "recurring",
  "trading_pair":            "XBTCHF",
  "deposit_day":             24,
  "buy_hour":                8,
  "crypto_amount":           0.0001,
  "dip_threshold_percent":   5.0,
  "dip_buy_cooldown_hours":  2.0,
  "poll_interval_seconds":   300,
  "max_price":               65000,
  "max_monthly_amount":       1000
}
Requirements

What you need to run it

—

Docker & Docker Compose

The bot runs as a hardened Docker container. Docker 20.10+ and Docker Compose 1.29+ are required. No other runtime dependencies — the bot uses Python's standard library only.

—

A funded Kraken account

Deposit fiat (CHF, EUR, USD…) via bank transfer before starting the bot. The bot reads the balance on startup and after every poll tick — it won't buy if the balance is zero.

—

A Kraken API key

Create a key under Account → Security → API → Create API key. Name it (e.g. dca-bot), enable only the two permissions below, and optionally restrict to the server's IP address. Kraken shows the secret only once — copy it immediately.

Enable

  • Query Funds — read fiat and crypto balances
  • Create & Modify Orders — place market buys

Never enable

  • Withdraw Funds — would allow draining the account if the key leaks
  • Any admin or transfer permissions

Deploy

shell
# One-time setup
cp main.py config.json Dockerfile docker-compose.yml /your/production/path/
echo "KRAKEN_API_KEY=your_key"     >> .env
echo "KRAKEN_API_SECRET=your_secret" >> .env
touch transactions.json

# Start
docker compose up -d --build

# Watch logs
docker compose logs -f

# Update (transactions.json is never touched)
cp main.py config.json /your/production/path/
docker compose up -d --build
Security

How the bot is hardened

The attack surface is minimal by design. No web server, no remote access, no third-party packages, no shell calls. The only outbound communication is HTTPS to Kraken's API.

Credentials

  • API keys come exclusively from environment variables, never from config.json
  • The .env file lives only on the production host and is never committed to git
  • Keys are never logged or printed at any point

Docker container

  • Runs as non-root user krakenuser (UID 1000)
  • All Linux capabilities dropped (cap_drop: ALL)
  • No privilege escalation (no-new-privileges: true)

Application

  • Zero third-party packages — stdlib only (urllib, hmac, hashlib, json)
  • No eval, no pickle, no subprocess calls
  • All config values validated on startup — fails fast with a clear error

Data

  • config.json and transactions.json are volume-mounted — never baked into the image
  • Rebuilding the image never touches transaction history
  • No database — plain JSON, no injection surface
docker-compose.yml — security options
security_opt:
  - no-new-privileges:true
cap_drop:
  - ALL
restart: unless-stopped
volumes:
  - ./config.json:/app/config.json
  - ./transactions.json:/app/transactions.json
